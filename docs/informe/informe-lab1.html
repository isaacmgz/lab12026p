1. Introducción

El laboratorio plantea la construcción de una aplicación que simula las operaciones básicas de un banco: registrar clientes, transferir dinero entre cuentas y consultar el histórico de movimientos. El punto de partida fue el proyecto base entregado por el docente, que contenía la API REST en Spring Boot con su arquitectura por capas, y el ejercicio de entrega obligatoria consistía en desarrollar un frontend que consumiera las rutas definidas en los controladores, con al menos tres vistas: consulta de clientes, transferencia de dinero y tabla del histórico de transacciones por cliente.

El trabajo realizado va un paso más allá del mínimo solicitado. Antes de escribir la primera línea del cliente web se ejercitó la API existente con peticiones reales, lo que permitió detectar defectos funcionales de fondo: el más grave permitía enviar un monto negativo y, en consecuencia, transferir dinero en sentido contrario al solicitado. Por esa razón el informe documenta tanto la construcción del frontend como la corrección de las reglas de negocio que lo sustentan, ya que una interfaz solo puede ser confiable si el servicio que consume también lo es.

El resultado es una aplicación completa y verificada extremo a extremo: base de datos MySQL en contenedor, API REST con validación y manejo uniforme de errores, y un cliente web en React que consume esos servicios mediante Axios. Todo el proceso quedó versionado en un repositorio público con issues, ramas, pull requests e integración continua.

2. Objetivos

2.1. Objetivo general

Desarrollar un cliente web que consuma los servicios REST de la aplicación bancaria construida con Spring Boot, garantizando la comunicación efectiva entre las tres capas del sistema —interfaz de usuario, servicios de negocio y base de datos— y aplicando principios de arquitectura por capas, usabilidad y control de versiones.

2.2. Objetivos específicos

  1. Configurar un entorno de desarrollo reproducible que integre la API Spring Boot con una base de datos MySQL, parametrizando la conexión mediante variables de entorno.
  2. Verificar el comportamiento de los endpoints existentes e identificar y corregir los defectos funcionales que comprometen la integridad de los datos en las transferencias.
  3. Estandarizar las respuestas de error de la API conforme a la especificación RFC 9457, de modo que el cliente pueda interpretarlas y comunicarlas al usuario.
  4. Implementar las tres vistas exigidas por el laboratorio —consulta de clientes, transferencia de dinero e histórico de transacciones por cliente— empleando React y Axios.
  5. Incorporar la funcionalidad opcional de actualización y eliminación de clientes, respetando las reglas de integridad del histórico.
  6. Aplicar principios de experiencia de usuario e interfaz: retroalimentación de estados, prevención de errores, accesibilidad y diseño adaptable a dispositivos móviles.
  7. Validar el funcionamiento integral del sistema mediante pruebas automatizadas y la ejecución del flujo completo en un navegador real.
  8. Documentar el proyecto y gestionar su versionamiento en GitHub con un flujo basado en issues, ramas, pull requests e integración continua.

4. Arquitectura propuesta

El sistema adopta una arquitectura cliente-servidor de tres niveles, en la que cada nivel tiene una responsabilidad única y se comunica con el siguiente a través de un contrato explícito. El navegador ejecuta una aplicación de página única que nunca accede a la base de datos: toda operación se solicita a la API mediante HTTP con mensajes en formato JSON, y solo el servidor conoce las reglas de negocio y la persistencia.

4.1. Capas del servidor

El backend conserva la arquitectura por capas propuesta en la guía del laboratorio, con una responsabilidad clara en cada una:

CapaResponsabilidad
controllerExpone las rutas HTTP, valida el cuerpo de las peticiones y traduce el resultado a un código de estado.
serviceContiene las reglas de negocio y delimita la transacción de base de datos.
repositoryAcceso a datos mediante Spring Data JPA, con consultas derivadas del nombre del método.
entityEntidades JPA que representan las tablas customers y transaction.
dto + mapperObjetos de transferencia y mapeadores MapStruct; evitan exponer las entidades del dominio.
exceptionExcepciones de dominio y manejador global que las convierte en respuestas de error uniformes.

4.2. Organización del cliente web

El frontend replica esa separación de responsabilidades con una organización por funcionalidad: cada una de las tres áreas del negocio —customers, transfers y transactions— agrupa su propio acceso a la API, su modelo, sus componentes y sus páginas. Los elementos visuales reutilizables (botones, campos, tablas, diálogos y estados de carga, vacío y error) residen en un módulo compartido que actúa como sistema de diseño.

Se aplica además el patrón contenedor-presentación: las páginas obtienen los datos y coordinan las operaciones, mientras que los componentes solo reciben propiedades y emiten eventos. Esto mantiene la lógica concentrada en pocos archivos y permite probar los componentes de forma aislada.

4.3. Flujo de una transferencia

  1. El usuario selecciona las cuentas de origen y destino e ingresa el monto; el cliente valida localmente que las cuentas sean distintas, que el monto sea positivo, con máximo dos decimales, y que no supere el saldo disponible.
  2. Tras confirmar en el paso de revisión, Axios envía POST /api/transactions con las dos cuentas y el monto.
  3. El controlador valida el cuerpo de la petición mediante anotaciones de Bean Validation; si algo falla responde 400 indicando el campo afectado.
  4. El servicio abre una transacción, bloquea ambas cuentas en un orden consistente, verifica las reglas de negocio, actualiza los saldos con aritmética decimal exacta y registra el movimiento con la fecha asignada por el servidor.
  5. La respuesta 201 devuelve el comprobante; el cliente invalida su caché para que los saldos y el histórico se actualicen de inmediato en todas las vistas.

4.4. Decisiones de diseño relevantes

  • Atomicidad e integridad. La transferencia se ejecuta dentro de una única transacción con bloqueo pesimista de ambas cuentas, de modo que no puede quedar dinero descontado de una cuenta sin acreditarse en la otra, ni producirse condiciones de carrera entre transferencias simultáneas.
  • Errores interpretables por el cliente. Todas las respuestas de error siguen la especificación RFC 9457 (application/problem+json), con un mensaje legible y, en los errores de validación, el detalle por campo. Gracias a ello la interfaz muestra el mensaje junto al campo que lo origina.
  • Inmutabilidad del histórico. El número de cuenta y el saldo no se modifican desde los endpoints de cliente: el saldo solo cambia por transferencias, y no se permite eliminar clientes con movimientos registrados.
  • Configuración externa. Las credenciales y puertos se leen de variables de entorno con valores por defecto para desarrollo local, lo que permite ejecutar el sistema en otro equipo sin modificar el código.

5. Procedimiento

El desarrollo se organizó en fases; cada una corresponde a un issue en el repositorio y se integró a la rama principal mediante un pull request con su respectiva verificación.

5.1. Preparación del repositorio

Se creó un fork del repositorio base del docente, con lo que se conserva el commit inicial y la trazabilidad respecto al proyecto original. Sobre el fork se definieron ocho issues —uno por unidad de trabajo—, un hito de entrega y un flujo de trabajo basado en ramas nombradas por tipo (feat/, fix/, build/, docs/), commits con formato Conventional Commits y pull requests que cierran su issue.

5.2. Entorno reproducible

Se añadió un archivo compose.yaml que levanta MySQL 8.4 con comprobación de salud, y se parametrizó la conexión mediante variables de entorno. Adicionalmente se corrigieron dos conflictos de dependencias del proyecto base: la versión de jackson-databind fijada manualmente (2.15.0) convivía con los demás artefactos de Jackson gestionados por Spring Boot (2.19.4), y la versión de Lombok declarada no compila en JDK recientes. Al delegar ambas versiones a Spring Boot, el proyecto compila y arranca sin advertencias.

5.3. Diagnóstico de la API existente

Antes de construir el cliente se ejercitaron los endpoints con peticiones reales contra la base de datos. La prueba consistió en crear dos clientes con saldos conocidos y ejecutar transferencias con valores límite. El resultado más relevante fue el siguiente:

POST /api/transactions
{"senderAccountNumber":"1001","receiverAccountNumber":"1002","amount":-50}

Respuesta: 200 OK
Saldos antes:    1001 = 500.00      1002 = 100.00
Saldos después:  1001 = 550.00      1002 =  50.00

Es decir, un monto negativo invertía el sentido de la operación y permitía extraer dinero de la cuenta destino. El diagnóstico reveló además otros defectos, resumidos en la tabla siguiente.

6. Conclusiones

  1. La separación en capas demostró su utilidad práctica durante la corrección de defectos: las reglas de negocio de la transferencia se concentraron en la capa de servicio sin modificar controladores ni repositorios, y el cliente web no requirió cambio alguno porque el contrato de la API se mantuvo estable.
  2. Probar la API antes de construir la interfaz resultó determinante. El defecto del monto negativo era invisible desde el código, pero evidente al ejercitar el endpoint con valores límite; construir el frontend sobre esa base habría producido una aplicación que mostraba saldos incorrectos con total normalidad.
  3. La atomicidad no es opcional en operaciones financieras. Ejecutar las tres escrituras de una transferencia sin una transacción única deja abierta la posibilidad de que el dinero se descuente de una cuenta y no llegue a la otra ante cualquier fallo intermedio.
  4. Adoptar un estándar para los errores (RFC 9457) simplificó notablemente el cliente: un único punto de traducción convierte cualquier error en un mensaje comprensible y, cuando corresponde, lo asocia al campo del formulario que lo provocó.
  5. Los DTO y los mapeadores evitan exponer las entidades del dominio y permiten que la API evolucione sin que el esquema de la base de datos condicione la respuesta, a costa de un código de mapeo que MapStruct genera automáticamente.
  6. La validación en el cliente mejora la experiencia, pero no sustituye a la del servidor: el cliente previene errores antes de enviar la petición, mientras que el servidor garantiza la integridad frente a cualquier consumidor de la API.
  7. El flujo de versionamiento con issues, ramas y pull requests pequeños hizo que cada cambio fuera revisable de forma independiente y que el historial del proyecto explique por sí mismo la evolución del trabajo.
  8. Como trabajo futuro se identifican tres mejoras: almacenar los importes monetarios como BigDecimal en la base de datos en lugar de coma flotante, incorporar autenticación y autorización, y documentar la API con OpenAPI/Swagger.
